# Релиз yd-mcp

Что происходит при релизе, кто это делает и где ломается. Правила коммитов — скилл
`git-commit`; здесь конвейер целиком.

**Релиз запускает пользователь мерджем PR на GitHub, не ты.** Твоя роль — подготовить,
проверить, объяснить и разобрать поломку. Мерджить PR, пушить в `main`, дёргать
`workflow_dispatch` — только по прямой просьбе.

## Конвейер

```text
ветка задачи ──PR──▶ dev ──PR──▶ main
                              │
                              ├─ CI (build+test, node 22/24/26) ──▶ ci-ok
                              │
                              └─ workflow_run: CI success + event=push
                                     │
                                     ├─ Release: npx semantic-release
                                     │    версия → package.json
                                     │    CHANGELOG.md
                                     │    тег + GitHub release
                                     │    chore(release): x.y.z [skip ci] в main
                                     │
                                     └─ Back-merge: main ──▶ dev
```

Ключевые свойства, которые легко забыть:

- **`main` наполняется только мерджем PR из `dev`.** Прямой пуш отбивает хук `pre-push`
  локально и рулсет на стороне GitHub.
- **Релиз стартует не по пушу, а по завершению workflow «CI»** на `main`
  (`workflow_run`), и только при `conclusion == success` **и** `event == push`. Прогоны
  CI на pull_request отфильтрованы — иначе релиз уезжал бы с ещё не влитого PR.
- **`ci-ok`** — агрегирующая джоба и единственная точка для required status check: имена
  матричных джоб меняются вместе с матрицей, её имя — нет.
- **`LEFTHOOK: "0"`** в релизном workflow: локальные хуки запрещают коммит на `main`, а
  релизный коммит делается именно там.

## Что делает semantic-release

Читает conventional-коммиты, попавшие в `main` с прошлого тега, и по ним:

1. считает следующую версию (SemVer);
2. пишет `CHANGELOG.md` (секции дефолтного пресета `angular`, на английском);
3. коммитит `CHANGELOG.md` + `package.json` + `package-lock.json` как
   `chore(release): x.y.z [skip ci]`;
4. ставит тег и создаёт GitHub release.

**Публикация в npm включена** (`npmPublish: true`): пакет уезжает в реестр тем же прогоном,
что ставит тег. Аутентификация — `NPM_TOKEN` в env шага Release, токен типа **Automation**:
у обычного publish упирается в 2FA, подтвердить которую в CI некому.

Сборку перед публикацией запускает не workflow, а хук `prepublishOnly` в `package.json` —
`npm publish` вызывает его сам. Поэтому шага `npm run build` в релизном workflow нет, и
добавлять его не нужно: `dist/` соберётся при публикации.

`registry-url` в setup-node **не задавать**: setup-node пишет свой `.npmrc`, плагин —
свой, и они конфликтуют. Токена в переменной достаточно.

Provenance (значок «Built and signed on GitHub Actions») пока не включён. Для него нужны
`permissions: id-token: write` у джобы `release` и `NPM_CONFIG_PROVENANCE: true` в env шага
Release; остальные условия уже выполнены — репозиторий публичный, `repository` в
`package.json` совпадает с реальным.

**Тип коммита → релиз.** Своей политики нет: в `.releaserc.json` не задано ни `preset`,
ни `releaseRules`, работают дефолты semantic-release (Angular-конвенция).

| Тип | Релиз | В CHANGELOG |
|---|---|---|
| `feat` | minor | Features |
| `fix` | patch | Bug Fixes |
| `perf` | patch | Performance Improvements |
| `revert` | patch, если в теле есть `This reverts commit <sha>` | Reverts |
| `!` или футер `BREAKING CHANGE` — в любом типе | major | + BREAKING |
| `refactor` `docs` `chore` `ci` `build` `style` `test` | — | — |

Колонки совпадают: что двигает версию, то и видно пользователю. Релиза с пустой секцией
не бывает, а ветка без релизных типов даёт «нет изменений, требующих релиза» — это штатный
исход, а не сбой пайплайна.

## Подготовка релиза

Прогнать перед тем, как предлагать PR `dev` → `main`:

```bash
git log --oneline <последний-тег>..dev   # что уедет в релиз
npm run typecheck && npm run lint && npm test && npm run build
```

Посмотреть на список коммитов глазами и ответить:

- Есть ли ломающие изменения, не помеченные `!` или футером `BREAKING CHANGE`?
  Переименованное поле схемы, убранный инструмент, смена аннотации `READ`→`WRITE` —
  ломающие, даже если внутри «просто переложено».
- Нет ли `fix`, чинящего код, который никогда не выходил в релиз? Такой коммит даст в
  публичном чейнджлоге строку про баг, проживший час внутри ветки (см. «fix или fixup?»
  в скилле `git-commit`).
- Нет ли коммитов, описывающих логику, которой в коде уже нет?

Сухой прогон, если нужно увидеть будущую версию и заметки, ничего не публикуя:

```bash
npx semantic-release --dry-run --no-ci
```

Ему нужен `GITHUB_TOKEN` в окружении. Проси пользователя запустить самому
(`! npx semantic-release --dry-run --no-ci`), если токена под рукой нет.

## Разбор поломок

### Релиз не запустился

Проверять по порядку — условие в `release.yml` тройное:

1. **CI на `main` завершился успехом?** Красный CI → релиза нет по замыслу.
2. **`event == push`?** Прогон CI, вызванный `pull_request`, релиз не запускает. Значит
   PR ещё не влит.
3. **Есть ли релизные коммиты?** Если с прошлого тега приехали только `chore`/`ci`/`test`,
   semantic-release честно ничего не выпускает и пишет это в лог. Это не поломка.

Догнать вручную — `workflow_dispatch` на workflow «Release», по просьбе пользователя.

### Релиз упал на пуше в `main`

Почти всегда — про креды, и в workflow это уже учтено; если сломалось, смотри, не
разъехалось ли:

- **`persist-credentials: false`** в checkout обязателен. Иначе checkout прописывает
  `http.extraheader` со штатным `GITHUB_TOKEN`, заголовок `Authorization` перебивает
  креды в URL, который semantic-release собирает из PAT, и пуш уходит от
  `github-actions` — у которого bypass в рулсетах нет.
- **`SEMANTIC_RELEASE_PAT`, а не `github.token`**: пуш релизного коммита в защищённый
  `main` проходит только от личности, внесённой в `bypass_actors` рулсета.

### Back-merge упал

`main` после релиза содержит два коммита, которых нет в `dev`: мердж-коммит PR и
`chore(release)`. Без обратного мерджа копится дрейф — в `dev` врёт `package.json`, а
следующий PR показывает `CHANGELOG.md` как откат.

Job отдельный намеренно: его падение не красит сам релиз. Если упал — почини мерджем
вручную (по просьбе пользователя), не пропускай.

Две тонкости, заложенные в шаг и легко теряемые при правке:

- мерджится **`FETCH_HEAD`**, а не `origin/main`: устаревший remote-tracking ref смерджил
  бы до-релизный `main` и молча оставил дрейф;
- **`[skip ci]`** в сообщении обязателен — пуш от PAT, в отличие от штатного токена,
  запускает workflow, и CI прогнался бы второй раз на том же коде.

### Версия вышла не та, что ожидали

Причина всегда в типах коммитов, а не в semantic-release. Посмотри
`git log --oneline <тег>..main` и сверь с таблицей выше. Частое: ломающее изменение
приехало как `feat` без `!` → вышел minor вместо major.

**Исправлять переписыванием истории нельзя.** Релиз опубликован, тег и чейнджлог уже
процитировали эти коммиты. Правильный путь — следующий релиз с честным типом, при
необходимости `revert`. Если пользователь просит переписать — сначала объясни, чем это
грозит опубликованному релизу (см. `git-commit/references/history-rewrite.md`).

## Первый релиз

Пока его не было, ветки `main` на GitHub может не быть вовсе — это нормально, а не сбой.
Первый PR `dev` → `main` её и создаст.
