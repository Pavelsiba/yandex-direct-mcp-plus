# yd-mcp Code Style

Проектные конвенции — код-стайл и то, что не влезло в `CLAUDE.md`. Читать/применять на
**любой задаче с кодом**: планирование раскладки, новая Zod-схема, новый инструмент,
хелпер — **и до правок, не только на `edit`**.

**Разделение с `CLAUDE.md`.** Там — обязательные инварианты в одну-две фразы (деньги, ID,
перечисления, ошибки, «update = полная замена», детерминизм, язык). Здесь — их глубина и
общий код-стайл. `CLAUDE.md` — источник правила, этот скилл — как его применять. Если
расходятся, прав `CLAUDE.md`; расхождение — повод сказать пользователю, а не выбрать
молча.

**Раскладка `src/` разложена по слоям** (03.09.2026, `refactor/tools-layout`):
`app/`, `tools/<домен>/{schema,handler,tool}.ts`, `shared/{api,lib,config}/`, `testing/`.
Новый инструмент — новый каталог домена плюс строка в `app/registry.ts`.

Импорты между слоями — subpath imports (`#shared/lib/id`), **внутри домена —
относительные** (`./schema.js`). Любой `#tools/**` внутри `src/tools/**` означает
обращение к соседнему инструменту и отбивается линтером.

## Направление зависимостей

`app → tools → shared`. Инструмент не импортирует инструмент, `shared` не знает про
`tools`. Сторожит `noRestrictedImports` в `overrides` секции `biome.json` — сейчас там
один блок, запрет импорта соседа из `src/tools/**`; политики между слоями дописываются
вместе с раскладкой.

Нужна логика двум инструментам — она уезжает в `shared/lib`, а не импортируется у соседа.
Соблазн «дёрнуть хендлер соседнего инструмента» почти всегда значит, что общий кусок —
чистая функция, которой место в `shared`.

## File Reading Discipline

**Rule:** Не читать файлы целиком, когда ответ выводится из знания механизма, а не из
структуры проекта.

**Когда НЕ читать:**

- Вопрос про механику JS/TS/Node/Zod (промисы, замыкания, типы, `z.infer`) → отвечать
  из знания.
- Массовый рефакторинг по паттерну → прочитать 2–3 примера, дальше `grep` нужного
  фрагмента + точечный `edit`, без полного чтения каждого из 30 файлов `src/tools/`.

**Когда читать:**

- Конкретный контракт инструмента или форма ответа Директа, которую нельзя вывести без
  кода/фикстуры.
- Незнакомый файл перед первым edit.
- Проверка инварианта перед изменением (что схема правда конвертирует рубли, что ID
  правда идёт через `idField`).

**Why:** сканирование шести файлов на вопрос про `z.coerce` — это тысячи токенов на
ответ, не требовавший ни одного чтения.

## Complexity Flags

**Rule:** Флажить пользователю, если:

1. **Файл инструмента 300+ строк** — вероятен разъезд по `schema.ts` / `handler.ts` /
   `tool.ts`, а если и после этого много — домен тянет на два инструмента.
2. **Схема инструмента с 10+ полями верхнего уровня** — модель на другом конце должна
   уметь её заполнить. Пересмотреть: обязательные vs опциональные, не пора ли разбить
   операцию.
3. **«Умный» хендлер** — делает несколько несвязанных дел подряд (проверил → сходил →
   слил → сконвертировал → отформатировал). Каждое дело — кандидат в мини-модуль.

No («умный» хендлер — четыре темы вперемешку):

```ts
export async function setCampaignNegativeKeywords(input: Input) {
  const current = await client.post("campaigns", "get", { ... })
  const existing = current.result.Campaigns[0]?.NegativeKeywords?.Items ?? []
  const merged = [...new Set([...existing, ...input.keywords])]
  if (merged.length > 4096) throw new Error("Слишком много минус-фраз")
  const body = { Campaigns: [{ Id: BigInt(input.campaignId), NegativeKeywords: { Items: merged } }] }
  const res = await client.post("campaigns", "update", body)
  // …ещё 40 строк: разбор *Results, LimitedBy, форматирование
}
```

Yes (сценарий из названных шагов; каждый шаг — свой модуль и свой тест):

```ts
export async function setCampaignNegativeKeywords(input: Input) {
  const existing = await fetchCampaignNegativeKeywords(input.campaignId)
  const merged = mergeNegativeKeywords(existing, input.keywords)   // чистая, тестируется без сети
  const res = await client.post("campaigns", "update", buildUpdateBody(input.campaignId, merged))
  return formatUpdateResult(res)
}
```

**Что делать при обнаружении:** НЕ молча рефакторить — сначала указать пользователю на
проблему, назвать число строк/полей, предложить варианты декомпозиции, дождаться решения.

### Критерий выноса — два вопроса, не один

Решая «выносить ли блок», спрашивать оба:

1. **Читаемость** — станет ли понятнее?
2. **Тестируемость** — появится ли шов, которого не было?

Второй вопрос **не подчинён первому и умеет переворачивать вердикт**. Блок, который по
читаемости выглядит нормально, может быть единственной причиной, по которой тест
невозможен или дорог.

Пример выше: слияние минус-фраз внутри хендлера по читаемости выносить не обязательно —
три строки. По тестируемости — обязательно: пока оно внутри, проверить объединение
(инвариант «Update = полная замена») можно только подделав два `fetch` подряд, и тест
будет про проводку, а не про слияние. После выноса `mergeNegativeKeywords` — обычная
чистая функция и обычный тест на дубли, регистр и порядок.

**Вынос помогает НЕ всегда.** Если в хендлере только диспетчер, а логика уже живёт в
`shared/lib`, вынос даст имя, но не шов; шов уже есть, просто не использован. Такой блок
выносят ради читаемости — и об этом стоит говорить прямо, не выдавая одно за другое.

**Куда выносить** решают границы, а не вкус: блоку нужен HTTP/токен → `shared/api`; блок
чистый и доменно-нейтральный (деньги, ID, пагинация, формат) → `shared/lib`; чистый и
специфичный для одного инструмента → рядом с ним, в его каталоге.

### Однотипное — в одном месте (проверять модуль целиком)

Разложив инструмент, пройти по нему ещё раз и спросить: **сущности одного класса лежат в
одном месте?** Каждое решение по отдельности бывает разумным, а вместе они противоречат
друг другу — и этого не поймает ни biome, ни тест: код валиден, границы соблюдены.

Типичные дыры в этом репозитории:

```ts
// ✖ лимиты: MAX_NEGATIVE_KEYWORDS уехал в config, а рядом голые литералы того же класса
z.array(z.string()).max(MAX_NEGATIVE_KEYWORDS)
z.array(z.string()).max(200)    // почему не в config?
z.string().max(4096)            // почему не в config?

// ✖ конвертация: рубли→микро в схеме кампаний, а в схеме ставок — руками в хендлере
```

**Проверка не «вынес ли я эту штуку», а «все ли однотипные лежат вместе».** Делать по
всему модулю разом, а не по ходу правки.

Граница «в config или инлайн»: **настройка → config** (`PAGE_LIMIT = 10_000` — крутилка),
**структурная константа → на месте** (`z.array(...).min(1, { error: "Список пуст" })` —
единица здесь определение непустоты, а не настройка).

### Обоснование константы протухает

Именованная константа заводится ради причины (общая для N мест, длинное выражение).
**Причина исчезает молча.** Схлопнул дубль в общий хелпер — и то, что было общим, стало
одноразовым; константа осталась, а вместе с ней комментарий, который теперь врёт.

**Правило: одноразовая константа — инлайн.** После каждого схлопывания дублей
перепроверять, живы ли ещё причины у соседних констант. Не защищать константу
обоснованием, которое было верно две правки назад.

## Схемы инструментов

Полные правила Zod v4 — `references/zod-v4.md`. Здесь то, что специфично для MCP.

**Код переведён на эти правила** (03.09.2026): `.describe()` и `z.enum()` в `src/` не
осталось, у всех 48 инструментов описано каждое поле — это сторожит тест по реестру
(`src/app/registry.unit.test.ts`).

Значения перечислений берутся из WSDL сервиса
(`curl -s "https://api.direct.yandex.com/v5/<service>?wsdl"` — отдаётся без токена),
а не со страниц справочника: те дают неполные списки, а неполный литерал отклоняет
валидный вызов. То, что подтвердить нечем, остаётся `z.string()` с перечислением
в описании.

**Схема — это документация для модели.** Её читает не человек в IDE, а модель на другом
конце протокола, и другого описания у неё нет. Отсюда три следствия:

1. **Перечисления — `z.literal([...])`, не `z.string()`.** Допустимые значения обязаны
   быть типом, а не прозой в описании.
2. **Описание на каждом поле** — через `.meta({ description })` (zod v4; `.describe()` —
   легаси v3). Коротко о смысле/происхождении/нюансе, а не пересказ типа.
3. **Единицы и формат — в описании обязательно.** «Ставка» бессмысленна; «ставка в рублях»
   — контракт. Для ID — «строка, десятичный ID кампании».

Тексты ошибок — `{ error: "..." }`, не `{ message: ... }`, и на русском.

**Конвертация — в схеме, не в хендлере.** Вход: рубли → микроединицы конвертирует схема
(`.transform`). Выход: микроединицы → рубли конвертирует `format`. Хендлер на миллион не
умножает — увидел `* 1_000_000` в хендлере, это находка.

**ID — через `idField`, никогда `z.coerce`.** `z.coerce.number()` на 19-значном ID принял
бы уже округлённое число и превратил его в правдоподобную строку — потеря точности стала
бы невидимой. Наружу десятичные строки, внутрь `BigInt`. Разбор и сериализация JSON —
только через `json-bigint` и только в `shared/api`; держит это GritQL-плагин Biome
(`plugins/no-native-json.grit`), исключения помечены в файлах строкой
`// biome-ignore-all lint/plugin`.

**Аннотация инструмента** (`READ` / `WRITE` / `IDEMPOTENT` / `DESTRUCTIVE`) выбирается по
реальной природе операции — на неё полагаются клиенты, чтобы решить, спрашивать ли
пользователя. `manage_*`, умеющий удалять, — `DESTRUCTIVE`, даже если обычно только
обновляет.

## Чистые хелперы

**Rule:** чистые хелперы (без обращений к сети, токену, часам) живут вне хендлера — на
уровне модуля или в `shared/lib`.

| Scope                                          | Location                          |
| ---------------------------------------------- | --------------------------------- |
| Используется в одном инструменте               | Над хендлером в том же файле      |
| Общий, привязан к домену инструмента           | Рядом с инструментом, в его каталоге |
| Переиспользуемый, доменно-нейтральный          | `shared/lib/`                     |

**Не плодить заранее:** общий модуль появляется **при использовании в 2+ местах**, не
заранее.

### Getter Pattern (lookup-таблицы)

Маппинг enum/union → объект конфига — **getter-функцией с inline lookup-таблицей**, не
`switch`/`if-else`. Директ отдаёт много таких перечислений (статусы кампаний, состояния
модерации, типы стратегий).

Yes:

```ts
/** Человекочитаемый статус кампании; неизвестный код — `UNKNOWN`. */
export const getCampaignStatus = (status?: CampaignStatus): { label: string; active: boolean } =>
  ({
    ACCEPTED: { label: "Принята", active: true },
    MODERATION: { label: "На модерации", active: false },
    REJECTED: { label: "Отклонена", active: false },
    DRAFT: { label: "Черновик", active: false },
    UNKNOWN: { label: "Неизвестен", active: false }
  })[status ?? "UNKNOWN"]
```

**Правила:** имя `get<Thing>Status`/`get<Thing>Label`/`get<Thing>Config`; явный return
type; fallback через `?? "DEFAULT_KEY"`; JSDoc с описанием fallback; большую таблицу — как
`const X_MAP = {...} as const` выше геттера.

Директ добавляет значения в перечисления без предупреждения — fallback обязателен, падать
на незнакомом статусе нельзя.

## Comments

**Rule:** комментариев — минимум. Допустимы два вида:

1. **Шапка модуля** — 1–2 строки: зачем файл существует и чем отличается от соседа.
2. **Точечный комментарий на нетривиальном месте** — то, чего код показать не может:
   неочевидное поведение API Директа, внешнее ограничение, причина странного решения.

Второй вид в этом проекте важнее обычного: половина странностей в коде — не наши, а
API. Такое фиксировать обязательно, с датой пробы, если знание добыто эмпирически.

Yes (комментарий несёт то, чего нет в коде):

```ts
// v5 отдаёт ошибку запроса телом с HTTP 200 — статус проверять бесполезно.
const error = parseRequestError(payload)

// NegativeKeywords.Items перезаписывается целиком: шлём объединённый список,
// иначе прежние минус-фразы молча пропадут.
const merged = mergeNegativeKeywords(existing, incoming)
```

No (пересказ кода — вырезать):

```ts
/** Конвертирует микроединицы в рубли. */
const microToRub = (value: bigint) => Number(value) / 1_000_000   // имя уже это сказало

// Получаем кампании
const campaigns = await listCampaigns()
```

**В тестах комментариев нет.** Название кейса уже говорит и что проверяется, и зачем.

**Проверка перед тем, как оставить комментарий:** если удалить эту строку — читатель
потеряет знание или просто текст? Потеряет знание → оставить.

**Язык — русский**: описания инструментов, `.meta({ description })`, тексты ошибок,
комментарии, коммиты.

## Variable Naming

Любой идентификатор с доменным смыслом — осмысленное имя. Никаких однобуквенных
(`c`, `k`, `r`, `e`).

```ts
campaigns.map((campaign) => ...)          // не (c) =>
items.reduce((total, item) => ..., 0)
keywords.filter((keyword) => ...)
```

**Исключения:** `(value, index)` — `index`/`idx` OK, `i` нет; `(prev, curr)` для reducer;
TS generics `T`/`K`/`V` (лучше `TItem`/`TKey`, если домен ясен).

**Поля тела запроса к Директу — как в API**, PascalCase и всё: `Ids`, `SelectionCriteria`,
`FieldNames`. Не переименовывать «для красоты»: расхождение с документацией дороже
консистентности. Наружу, в схему инструмента, они выходят уже в нашем camelCase.

## Destructuring

2+ обращения к полям одного объекта → деструктурировать в начале функции.

```ts
const { campaignId, keywords, limit } = input
if (!campaignId || keywords.length === 0) return EMPTY
```

**Исключения:** одно обращение — деструктуризация избыточна; методы оставлять на объекте
(потеря `this`); конфликт имён — переименовать через `:`.

## Anti-Patterns

### Число там, где должна быть строка

`Number(id)`, `parseInt(id)`, сравнение ID с числовым литералом, `JSON.parse` вместо
`json-bigint` вне `shared/api`. Каждое — потеря точности, которая выглядит работающей на
коротких ID из песочницы и ломается на боевых 19-значных.

### Множитель в хендлере

`* 1_000_000` или `/ 1_000_000` вне схемы и `format`. Конвертация в двух местах рано или
поздно случится дважды.

### Частичный update

Отправка одного элемента туда, где Директ перезаписывает коллекцию целиком
(`NegativeKeywords.Items`, сайтлинки, привязки наборов). Прежде чем «добавить одну
фразу» — прочитать текущее значение и отправить объединённое.

### Часы внутри хендлера

`Date.now()`, `new Date()` без аргумента, `Math.random()` в хендлере делают его
непроверяемым. Такие значения приходят параметром или из подменяемого хелпера.

### Обход запрета вместо остановки

Команда отбита хуком или правилом `deny` — и она переписывается так, чтобы правило не
сработало: `process["env"]` вместо `process.env`, другая утилита, другой флаг, строка
вынесена в файл. Выглядит как обход ложного срабатывания, работает как обход защиты.

Правильно: сказать пользователю, что именно понадобилось и обо что запрет ударил, и
попросить сделать это его. Значения секретов не выясняются командой ни при каких условиях —
ни длиной, ни префиксом, ни проверкой «задан ли». Полное правило — `CLAUDE.md`, раздел
про секреты; сам запрет — `.claude/hooks/deny-secrets.mjs`.

### NOTE-комментарии

Паттерны из ревью помечаются `// NOTE: <причина>`. Не оставлять — фиксить или
эскалировать. Нерешённое → открытый вопрос пользователю, не NOTE.

### Содержимое исходника в тексте команды

Файл правится инструментом (`Edit`/`Write`), а не heredoc'ом в шелле. В шелл уходят
команды, а не содержимое файлов: `cat > src/… <<'EOF'` кладёт весь текст модуля в текст
команды — и хук на `.env` отбивает правку из-за `process.env`, написанного внутри
исходника.

Сужать хук под такой случай нельзя: каждое исключение — готовый карман для обхода, и один
такой карман (вырезка `--env-file` перед проверкой) 05.09.2026 уже сработал. Ложное
срабатывание чинится сменой приёма, а не шаблона запрета.

## When to Apply

- Новый инструмент → каталог домена, дескриптор через `defineTool` из
  `#shared/lib/tool`, явный импорт в `app/registry.ts`, аннотация по природе операции,
  тест рядом с кодом
- Новая схема → `z.literal` для перечислений, `.meta({ description })` на каждом поле,
  единицы в описании, конвертация денег в схеме, ID через `idField`
- Правка хендлера → нет часов, нет множителя, нет разбора ошибок (это делает `shared`)
- Работа с коллекциями Директа → проверить, не «полная замена» ли это
- Любой `.ts` с логикой → Complexity Flags, комментарии, именование
- Правка любого файла → инструмент `Edit`/`Write`; шелл получает команды, а не текст
  исходников
