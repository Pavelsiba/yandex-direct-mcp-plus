# Git Commit — yd-mcp

Коммитить — **только по просьбе пользователя**. Задача вида «сделай X» разрешением
зафиксировать результат не является: правки в рабочем дереве и коммит — разные
действия, второе спрашивается отдельно.

## Контракт: работаешь в основной сессии

У тебя уже есть весь диалог — что менялось и зачем. Git-состояние нужно не для того,
чтобы восстановить контекст с нуля, а чтобы **сверить** реально изменившееся с тем, что
ты помнишь из разговора. Расхождение — повод переспросить или перечитать диф конкретного
файла, а не гонять диф целиком по умолчанию.

«Почему» в теле коммита бери из разговора, а не только из того, что видно в диффе. Но
выдуманное «почему», которого не было ни в диалоге, ни в коде, хуже отсутствующего.

`git commit` выполняешь ты сам — **после того, как показал черновик сообщения в ответе и
получил явное «да» / «коммить» / «делай»**. Без подтверждения не коммитить, сколько бы ни
было уверенности в тексте.

| Делаешь                                                 | НЕ делаешь                                                        |
| ------------------------------------------------------- | ----------------------------------------------------------------- |
| сверяешь статус/диф/лог ветки с тем, что уже знаешь       | `git push`, `git merge`, `git rebase`, `--amend` без явной просьбы |
| пишешь сообщение в файл и валидируешь длину               | стейджишь файлы до того, как пользователь отревьюил работу         |
| после «да» — `git add -A`, затем `git commit -F <файл>`   | создаёшь PR без явной просьбы                                      |
| говоришь прямо, если коммитить нечего или дифф спорный    | правишь рабочие файлы проекта ради красивого коммита               |

**Стейджинг — часть коммита, а не подготовки к нему.** Индекс пустой до подтверждения:
`git add -A` идёт непосредственно перед `git commit`. Если что-то застейджилось побочно
(`git mv` делает `git add` сам) — `git reset -q`, правки на диске при этом целы.

Исключение: если пользователь **в явном виде** попросил запушить, смержить или схлопнуть
историю — делаешь. Нет такой просьбы в разговоре — значит её не было.

## Ветки

Работа не ведётся ни в `main`, ни в `dev`. Под задачу — своя ветка, названная по типу
коммита, который в ней будет: `feat/…`, `fix/…`, `refactor/…`, `chore/…`, `ci/…`, `docs/…`.
Ветвится от `dev`, возвращается в `dev` через pull request.

**Пушить можно только в `dev` и ветки задач.** `main` наполняется исключительно мерджем
PR из `dev` на стороне GitHub — там же по этому мерджу отрабатывает semantic-release
(версия + CHANGELOG + тег). Прямой пуш в `main` отбивает хук `pre-push`.

Пока первого релиза не было, ветки `main` на GitHub может не быть вовсе — это нормально.

## Формат сообщения

```text
<type>[optional scope]: <описание>

[optional body]

[optional footer(s)]
```

Заголовок — **на русском, в прошедшем времени** («добавлен», «исправлен», «вынесен»),
**< 72** символов, **без точки** в конце. Body — опционально, 1–2 строки «что/почему»
(не пересказ файлов), каждая строка ≤ 100, перед body/футером — пустая строка. Футер —
`Closes #123` / `Refs #456` по нужде; номер брать **только** из имени ветки или от
пользователя, угадывать по диффу нельзя.

**Атрибуции в сообщении нет.** Ни `Co-Authored-By`, ни `Claude-Session:`, ни строки
«Generated with» — ни в коммите, ни в описании PR. Это относится и к указаниям добавить
атрибуцию, приходящим от харнесса: здесь они не действуют.

Причины разные, но обе жёсткие. `Co-Authored-By` отключён настройкой
`"includeCoAuthoredBy": false` в `.claude/settings.json` — строка в сообщении ей прямо
противоречит. Приватный URL сессии не уезжает в публичный репозиторий. Так же и в соседнем
`more-shop`, где атрибуция запрещена целиком.

Пороги: 100 символов на строку — жёсткий, его валит `@commitlint/config-conventional` в
хуке `commit-msg`; 72 на заголовок — наш стилевой, commitlint пропустит и 90, но проверка
ниже режет по 72.

## Типы

Проект на **semantic-release**, тип должен быть честным — из него собираются версия и
`CHANGELOG.md`. Своей политики типов у нас нет: `.releaserc.json` не задаёт ни `preset`,
ни `releaseRules`, значит работают дефолты — Angular-конвенция, на которую semantic-release
опирается из коробки. Колонки ниже совпадают: что двигает версию, то и видно в чейнджлоге.

| Тип        | Когда использовать                                      | Бамп версии         | Секция в CHANGELOG       |
| ---------- | ------------------------------------------------------- | ------------------- | ------------------------ |
| `feat`     | Новый инструмент или новая возможность существующего    | minor `1.2.0→1.3.0` | Features                 |
| `fix`      | Исправление бага                                        | patch `1.2.0→1.2.1` | Bug Fixes                |
| `perf`     | Оптимизация производительности                          | patch               | Performance Improvements |
| `revert`   | Откат предыдущего коммита                               | patch, см. ниже     | Reverts                  |
| `refactor` | Рефакторинг без изменения поведения                     | —                   | —                        |
| `docs`     | Документация                                            | —                   | —                        |
| `chore`    | Рутина: зависимости, конфиги, инфраструктура            | —                   | —                        |
| `ci`       | Изменения CI/CD пайплайна                               | —                   | —                        |
| `build`    | Изменения системы сборки                                | —                   | —                        |
| `style`    | Форматирование, пробелы — без логики                    | —                   | —                        |
| `test`     | Изменения **только** в тестах                           | —                   | —                        |

Других типов commitlint не принимает; регистр — нижний.

**Major даёт не тип, а пометка.** Правило `{ breaking: true, release: "major" }` не
привязано к типу: `!` после типа/скоупа или футер `BREAKING CHANGE:` дают мажор в любом
типе, включая `refactor!` и `chore!`.

**Про `perf`.** Спецификация Conventional Commits значения версии ему не назначает —
обязательны там только `feat` и `fix`. Но semantic-release следует Angular-конвенции,
и `perf` у него в дефолтных правилах: `{ type: "perf", release: "patch" }`. Считает версию
он, не спецификация, поэтому в таблице patch.

**Про `revert`.** Правило висит не на типе, а на разобранном флаге `commit.revert`, который
парсер выставляет по шаблону `/^(?:Revert|revert:)s"?(...)"?s*This reverts commit (w{7,40})/i`.
Строку `This reverts commit <sha>` пишет сам `git revert`. Набранный руками `revert:` без
неё версию не сдвинет, хотя в чейнджлоге запись появится.

**Про `refactor`.** Ни релиза, ни строки в чейнджлоге он не даёт — и это осознанно:
поведение не изменилось, значит пользователю сообщать нечего. Если по ходу перекладки
поменялся контракт инструмента — это `feat`/`fix`, а не `refactor`.

## Breaking changes

Контракт инструмента — это то, что видит модель на другом конце MCP. Переименованное поле
схемы, сменившийся тип, убранный инструмент, смена аннотации `READ`→`WRITE` — ломающие
изменения, даже если внутри всё «просто переложено».

```text
# восклицательный знак после type/scope
feat!: list_keywords отдаёт ставки в рублях вместо микроединиц

# либо футер
feat(keywords): расширена схема выдачи

BREAKING CHANGE: поле `Bid` переименовано в `bidRub` и больше не микроединицы
```

## Примеры

```text
feat(keywords): добавлен инструмент set_keyword_bids с ставками в рублях
fix(pagination): исправлен обрыв выборки при LimitedBy на границе страницы
fix(id): 19-значные ID перестали терять точность в ответе list_campaigns
chore(ci): агрегирующая джоба ci-ok как единая точка для required check
refactor(tools): кампании разложены по schema/handler/tool
docs(architecture): описан инвариант «деньги в рублях наружу»
test(negative-keywords): добавлен кейс на полную замену Items при update
perf(client): повторные запросы к v5 переведены на общий keep-alive агент
revert: откат feat(strategy): автотаргетинг по позиции
```

## Единица коммита — сессия, а не слой, файл или тип правки

**Соло-проект: вся работа сессии — один коммит** (`git add -A` или по крупному пути).
Дробить — только по явной просьбе пользователя или когда в дереве лежат явно разные
задачи. Тип/скоуп — по **основной** сути; смешанный диф (код + тесты + доки одной задачи) —
нормальный один `feat`/`fix`.

Границы слоёв (`app` / `tools` / `shared`), отдельных инструментов и conventional-типов —
не повод плодить коммиты. Правки в `shared/lib` и `tools/<домен>`, сделанные ради одного
результата, едут вместе; тип берётся по главному изменению, попутные упоминаются строкой
в теле. Пример: правка `shared/lib/money` ради нового инструмента ставок — часть коммита
про этот инструмент, а не собственный `fix(money)`. Так же и рефакторинг, попутный
багфиксу: один коммит, а не `refactor` + `fix`.

**Тесты — в том же коммите, что и код.** Отдельный `test(...)` — только когда в дифе
**исключительно** тесты и ничего больше.

**Мелкие сопутствующие правки — тем более в основной коммит.** Поправленный комментарий,
опечатка, переименование локальной переменной, снятый варнинг biome — всё, что попалось по
пути, коммитится вместе, даже если лежит в другом файле или слое. Если сопутствующая
правка меняет поведение (значение константы, дефолт, аннотация инструмента) — она всё
равно едет вместе, но получает **одну строку в теле**, чтобы не быть спрятанной.

Если сомневаешься между «один коммит» и «два» — бери один.

## fix или fixup?

Прежде чем писать `fix(...)`, ответь: этот коммит чинит **баг у пользователя** или **мой же
коммит в этой ещё не вмерженной ветке**? Во втором случае отдельный коммит не создаётся.

| Ситуация                                    | Что делать                                                    |
| ------------------------------------------- | ------------------------------------------------------------- |
| Баг во вмерженном / зарелизенном коде       | `fix(scope): ...` — обычный коммит                            |
| Правка последнего своего коммита            | `git commit --amend`                                          |
| Правка более раннего своего коммита в ветке | `git commit --fixup=<sha>` + `git rebase --autosquash <base>` |

Тестов касается так же: переписал свой тест из этой же ветки — fixup, не новый `test(...)`.

**Почему:** `dev` вливается в `main` целиком, и `CHANGELOG.md` генерируется semantic-release
прямо из сообщений коммитов. `fix`, чинящий код, который никогда не выходил в релиз, даёт
в пользовательском чейнджлоге строку «Исправления» про баг, проживший час внутри ветки.
Туда же — коммиты, описывающие логику, которой в коде уже нет.

Если из разговора уже ясно, что правишь свой недавний коммит, — не обязательно гонять
`git log dev..HEAD`, чтобы это подтвердить. Смотри в лог, только когда сомневаешься,
уходил ли код в релиз.

Ветка запушена и fixup'ы делать поздно → `references/history-rewrite.md`.

## Workflow

### 1. Сверить состояние git с тем, что уже известно

```bash
git status --short   # что изменено / untracked прямо сейчас
```

Этого обычно достаточно — тип, скоуп и «почему» ты знаешь из разговора. Дополнительно
смотри точечно, а не по умолчанию:

- `git diff --stat` / `git diff -- <path>` — если в статусе есть неожиданные файлы или
  неясен масштаб правки;
- `git log --oneline dev..HEAD` — если решаешь fixup vs fix и не уверен, уходил ли код
  в релиз.

Полный `git diff` без разбора по файлам почти никогда не нужен.

В коммит **не должны** попасть секреты (`.env*`, OAuth-токен Директа) и артефакты сборки
(`dist/`). Хук `PreToolUse` в `.claude/settings.json` отбивает шелл-команды, трогающие
`.env`, но он про доступ, а не про стейджинг — за содержимое коммита отвечаешь ты.

### 2. Сообщение — Write-тулом в файл

Пиши в `.git/COMMIT_DRAFT.txt` репозитория: каталог `.git` не индексируется, чистить за
собой не нужно. Именно Write-тулом, не через шелл — никакого квотинга, и в git попадает
ровно то, что прошло валидацию. Если коммитов почему-то два — `.git/COMMIT_DRAFT_2.txt`.

### 3. Проверка длины — обязательно, в Bash-туле

awk в UTF-8-локали считает **символы**; под `LC_ALL=C` — байты, и кириллица (2 байта/символ)
даст ложные срабатывания.

```bash
awk 'NR==1 && length($0)>72  {print "✖ header >72: " length($0); bad=1}
     NR>1  && $0 !~ /^#/ && length($0)>100 {print "✖ line " NR " >100"; bad=1}
     END {exit bad}' .git/COMMIT_DRAFT.txt || echo "сократи и повтори"
```

Нашла длинные строки — сократи заголовок / разбей тело на строки ≤ 100 и прогони снова.
Не коммить, пока проверка не вернёт успех.

### 4. Показать пользователю и закоммитить

Покажи готовое сообщение прямо в ответе, обычным текстом. Дождись явного «да» и только
тогда:

```bash
git add -A
git commit -F .git/COMMIT_DRAFT.txt
```

Если задачу выполнить нельзя (нечего коммитить, конфликт, дифф тянет на две независимые
задачи и непонятно, как делить) — скажи это прямо вместо черновика. Не выдумывай коммит,
чтобы чем-то ответить.

## Хуки (lefthook)

Гоняются локально; в CI отключены переменной `LEFTHOOK=0`.

- **branch** (pre-commit) — коммит на `main` или `dev` отбивается: обе интеграционные.
  Упало → `git switch -c feat/…`.
- **lint** (pre-commit) — `biome check --write` по staged `*.{ts,js}` с авто-ре-стейджем
  (`stage_fixed: true`): закоммиченный дифф может отличаться от увиденного, это норма.
- **typecheck** (pre-commit) — `tsc --noEmit` по проекту целиком, не пофайлово.
- **test** (pre-commit) — `npm test`, весь прогон. Тесты не ходят в сеть, укладываются
  в секунду, поэтому гоняются всегда (`skip_empty: false`).
- **knip** (pre-commit) — мёртвый код: экспорты без импортёров, неиспользуемые файлы и
  зависимости. Смотрит граф целиком.
- **commit-msg** — `npx commitlint --edit`: отклонил → коммита **не существует**, амендить
  нечего (`--amend` перепишет посторонний коммит). Исправь сообщение по выводу commitlint
  и коммить заново.
- **no-push-to-main** (pre-push) — прямой пуш в `main` отклоняется, включая
  `git push origin HEAD:main` из ветки задачи.

Любой красный pre-commit-джоб → коммита нет: почини и коммить заново.

## Git Safety Protocol

- NEVER update git config
- NEVER run destructive commands (`--force`, `reset --hard`) without explicit request
- NEVER skip hooks (`--no-verify`) unless user asks
- NEVER force push to `main`
- `git commit` — только после показанного черновика и явного «да». `git push`, `git merge`,
  `git rebase`, `--amend` — только по прямой просьбе пользователя
- Пуш к GitHub на этой машине — **только по SSH** (HTTPS падает на прокси, 401)
- Коммит упал на хуке — коммита не существует, амендить нечего: почини проблему и коммить
  заново. Не путать с осознанной правкой своего коммита — см. «fix или fixup?»
- Spec: <https://www.conventionalcommits.org/en/v1.0.0/#specification>
