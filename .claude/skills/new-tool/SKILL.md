# Новый инструмент yd-mcp

Порядок и решения, которые нужно принять осознанно. Код-стайл и правила схем — скилл
`yd-conventions` (+ `references/zod-v4.md`), инварианты — `CLAUDE.md`, обоснования —
`docs/architecture.md`.

**Прежде чем писать код** — проверь `docs/roadmap.md`: инструмент, скорее всего, уже
описан там с приоритетом (P1/P2/P3), и в описании сказано, зачем он и что закрывает.
Если задача закрывает пункт роадмапа — этот пункт правится в том же коммите.

## Шаг 0 — Решить четыре вопроса до кода

1. **Это новый инструмент или параметр существующего?** 48 инструментов уже есть.
   Ещё один `list_*`, отличающийся одним фильтром, хуже, чем поле в существующей схеме:
   модель на другом конце выбирает из списка, и близнецы её путают.
2. **Какой сервис и метод API?** v5 (`apiPost`), Live v4 (`apiV4` — только финансы,
   баланс), отчёты (`apiReport`). Ошибиться легко: баланс есть **только** в v4.
3. **Какая аннотация?** См. ниже — от неё зависит, спросит ли клиент пользователя.
4. **Это «полная замена»?** Если метод перезаписывает коллекцию целиком
   (`NegativeKeywords.Items`, сайтлинки, привязки наборов) — сценарий обязан сначала
   прочитать текущее значение и отправить объединённое. Это инвариант из `CLAUDE.md`,
   и его нарушение молча стирает пользовательские данные.

## Шаг 1 — Схема

Файл: `src/tools/<домен>.ts` (текущая плоская раскладка) или `tools/<домен>/schema.ts`
(целевая, см. `docs/architecture.md`). Новый домен заводится, когда в нём есть инструмент;
пустые каталоги заранее не плодим.

**Граница контракта — здесь и только здесь.** Имена параметров MCP — **snake_case**
(`campaign_id`, `ad_group_ids`): это внешний контракт, его видит модель, он зашит в чужие
промпты. Внутри TypeScript — **camelCase**. Перевод делает схема; хендлер получает
нормальный объект и про snake_case не знает.

```ts
export const setKeywordBidsSchema = z.object({
  keyword_ids: z.array(idField("ID ключевой фразы")).meta({
    description: "ID ключевых фраз — десятичные строки"
  }),
  bid: z.number().positive().optional().meta({
    description: "Ставка на поиске в рублях; сервер переведёт в микроединицы"
  }),
  strategy_priority: z.literal(["LOW", "NORMAL", "HIGH"]).optional().meta({
    description: "Приоритет фразы для автостратегии; по умолчанию NORMAL"
  })
})
```

Обязательное: `z.literal([...])` для перечислений, `.meta({ description })` на каждом
поле, единицы и формат в описании, `{ error: "..." }` для текстов ошибок, `idField()` для
ID, конвертация рублей — в схеме.

**Существующие соседние файлы на легаси-синтаксисе** (73 `.describe()`, 24 `z.enum()` на
03.09.2026) — не копируй из них. Массовый перевод — отдельная задача.

## Шаг 2 — Хендлер

```ts
export async function handleSetKeywordBids(
  params: z.infer<typeof setKeywordBidsSchema>
): Promise<string> {
  const data = await apiPost("keywordbids", "set", { KeywordBids: buildBids(params) })
  return formatResult(data)
}
```

Хендлер — **сценарий, а не свалка**. Чего в нём быть не должно:

- **умножения на миллион** — конвертацию делает схема (вход) и `format` (выход);
- **разбора ошибок API** — ошибку запроса ловит `assertNoApiError` в клиенте, per-item
  ошибки в `*Results` и `LimitedBy` разбирает `format`;
- **`Date.now()` / `new Date()` без аргумента / `Math.random()`** — такие значения
  приходят параметром или из подменяемого хелпера, иначе хендлер непроверяем;
- **нативного `JSON.parse`/`stringify`** — только `json-bigint` и только в клиенте;
  GritQL-плагин Biome (`plugins/no-native-json.grit`) это ловит.

Возвращает **строку** (`Promise<string>`) — так устроен `reg()`; форматирование делает
`formatResult(data, opts)`. Для Live v4 передавай `{ money: false }`: там суммы уже в
валюте аккаунта, второй конверсии не нужно.

Логика, нужная двум инструментам, едет в `shared` (сейчас — `src/format.ts`, `src/id.ts`,
`src/pagination.ts`), а не импортируется у соседнего инструмента: `noRestrictedImports`
в `biome.json` запрещает импорт соседа из `src/tools/**`.

## Шаг 3 — Аннотация

Определены в `src/index.ts`. Выбор — по **реальной природе операции**, на неё полагаются
клиенты, чтобы решить, спрашивать ли пользователя перед вызовом.

| Аннотация     | Хинты                                            | Когда |
| ------------- | ------------------------------------------------ | ----- |
| `READ`        | `readOnlyHint: true`                             | Ничего не меняет: любой `list_*`, `get_*` |
| `WRITE`       | `readOnlyHint: false`                            | Создаёт или меняет: `create_*`, `add_*`, `update_*` |
| `IDEMPOTENT`  | `readOnlyHint: false, idempotentHint: true`      | Повторный вызов с теми же аргументами даёт тот же результат: `set_*` |
| `DESTRUCTIVE` | `readOnlyHint: false, destructiveHint: true`     | Может удалить или необратимо испортить: `delete_*`, `manage_*` с удалением |

Все — с `openWorldHint: true`: инструмент ходит во внешнюю систему.

Две ловушки:

- **`set_*` — это `IDEMPOTENT`, но только если правда полная замена.** Инструмент,
  который дописывает к существующему, идемпотентным не является.
- **`manage_*`, умеющий удалять, — `DESTRUCTIVE`**, даже если обычно только обновляет.
  Аннотация описывает худший случай, а не типичный.

## Шаг 4 — Регистрация

**Сейчас** — вызов `reg()` в `src/index.ts`, в секции своего домена (там разделители вида
`// ─── Кампании ───`), плюс импорт схемы и хендлера сверху:

```ts
import { handleSetKeywordBids, setKeywordBidsSchema } from "./tools/bids.js"

reg(
  "set_keyword_bids",
  "Ставки по фразам",
  "Установка ставок на поиске и в сетях для ключевых фраз. Ставки — в рублях.",
  setKeywordBidsSchema.shape,
  IDEMPOTENT,
  handleSetKeywordBids
)
```

Расширение `.js` в импорте обязательно — `moduleResolution: NodeNext`.

**Целевое** — дескриптор `defineTool` рядом с хендлером и явный импорт в
`app/registry.ts`. Функции `defineTool` ещё нет, она вводится вместе с раскладкой.

**Реестр собирается явными импортами, не глобом.** Glob прячет инструмент от knip — тот
перестаёт видеть, кто что использует, и начинает считать живые экспорты мёртвыми.

**Описание инструмента** — то, по чему модель решает, вызывать ли его. Пиши, что он
делает и в каких единицах отдаёт результат («Бюджеты — в рублях»), а не пересказ имени.

## Шаг 5 — Тест

Тест — рядом с кодом, `*.unit.test.ts`, сеть не трогает: `fetch` подменяется глобально
до импорта модуля (`vi.stubGlobal`), токен кладётся в `process.env` тоже до импортов,
сам модуль импортируется динамически внутри кейса.

Проверять **обе стороны маппинга** — тест, проверяющий одну, пропускает половину:

1. **Что ушло в Директ.** Тело запроса: деньги — микроединицами, ID — строками, поля в
   PascalCase как в API. Для ID сверяй **сырую строку тела** (`rawBody`), а не
   распарсенный объект: нативный `JSON.parse` в самом тесте округлит 19-значный ID, и
   тест зазеленеет на сломанном коде.
2. **Что вернулось наружу.** Фикстуру ответа прогони через реальный хендлер и проверь
   точные значения: рубли числом, ID строкой посимвольно, разобранные per-item ошибки.

Точные ассерты, не `toBeDefined`: `expect(body.Bid).toBe(30_000_000)`, а не «ставка
задана». Форму реального ответа Директа, если она неочевидна, снимай пробой в песочнице —
скилл `direct-probe`, не угадывай по документации.

## Шаг 6 — Проверки перед сдачей

```bash
npm run typecheck
npm run lint          # biome
npm run lint:dead     # knip — новый экспорт без импортёра он посчитает мёртвым
npm test
npm run build         # MCP-клиенты запускают dist/index.js, а не TypeScript
```

`npm run build` — не формальность: без него клиент продолжит работать со старой сборкой,
и «инструмент не появился» будет выглядеть как баг регистрации.
