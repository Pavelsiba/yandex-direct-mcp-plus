# Ревью тестов yd-mcp

Ревьюишь **существующие** тесты, а не пишешь новые. Цель одна: чтобы каждый тест ловил
реальную регрессию поведения, а не подтверждал, что «код — это код».

Стек-контекст: Vitest, Node, TypeScript, Zod v4, `@modelcontextprotocol/sdk`, `json-bigint`.
Внешняя система — API Яндекс.Директа v5/v4. Конвенции кода — скилл `yd-conventions`,
архитектура — `CLAUDE.md` и `docs/architecture.md`. Здесь только качество тестов.

**Уровни и имена** (`vitest.config.ts`, проекты `unit` и `int`):

- `*.unit.test.ts` — **без сети**: подменён транспорт (`setTransport` в
  `shared/api/fetch.ts`), в глобальном `fetch` лежит заглушка-сторож. Проверяем тело
  запроса к Директу и разбор ответа — там живут ошибки маппинга.
- `*.int.test.ts` — против **боевого API**, сеть настоящая, `fileParallelism: false`
  (аккаунт один на прогон). Тестовой среды у Директа нет с июля 2026.

Имя обязано соответствовать уровню: настоящий `fetch` внутри `*.unit.test.ts` — дефект сам
по себе (критерий 6). `npm test` гоняет **только unit** — int вынесен в отдельный
`npm run test:int`, чтобы сетевой прогон нельзя было получить случайно (его же зовут
lefthook и CI).

**Пишущие int-тесты идут по боевому аккаунту.** Цель — только кампания-полигон в черновике
(ID — в `CLAUDE.local.md`), и только по явной просьбе пользователя. Процедура и проверка
цели — скилл `direct-probe`.

---

## Фаза 0 — Сбор

1. Определи набор файлов: аргумент скилла → иначе изменённые/untracked
   `*.unit.test.*` / `*.int.test.*` из `git status` → иначе спроси, что ревьюить.
2. Для КАЖДОГО теста прочитай **исходник тестируемого модуля** (инструмент, схему,
   хелпер в `shared`). Без него нельзя отличить бизнес-логику от механики — это не
   опционально.
3. Для каждого мока найди реальную зависимость (её сигнатуру/поведение), чтобы оценить,
   заменяем ли мок реальной реализацией.
4. Если тестовый файл **изменён**, а не создан — прочитай его `git diff` (к HEAD или к
   базе ветки). Ищи ослабления: конкретное значение → `toBeTruthy`/`toBeDefined`,
   `toHaveBeenCalledWith(...)` → `toHaveBeenCalled()`, удалённые кейсы. Понадобится для
   критерия 9.

## Фаза 1 — Проход по критериям

Пройди каждый `it` по чек-листу. Для находки фиксируй: файл:строка → в чём дефект → фикс.

### 1. Дубли — критерий «что сломается, если удалить»

На каждый `it`: **какую уникальную багу он ловит, которую не поймает ни один другой?**
Нет ответа → дубль, удалить. Частые формы:

- «минимальный» кейс поглощён «расширенным» (те же ветки, шире вход);
- атомарный кейс поглощён комбинированным;
- перечисление всех значений enum через **одну** ветку кода → один тест с `it.each`;
- один и тот же инвариант проверен и на уровне хелпера (`shared/lib`), и на уровне
  инструмента, хотя инструмент не добавляет своей логики;
- параметризованный кейс, где параметры не меняют проходимую ветку.

### 2. Кейсы-пустышки

Тест, зелёный при любой разумной реализации: проверяет тип, который гарантирует TS;
проверяет, что Zod / SDK / `json-bigint` работают (это тесты библиотеки, не наши);
повторяет уже покрытое. Убрать или усилить.

### 3. Механика vs поведение

Ассерты на детали реализации, а не на контракт:

- счётчики вызовов ради счёта (`calls.length > N`) → замени на проверку конкретного
  эффекта: какое **тело** ушло в Директ, что вернулось наружу;
- проверка порядка вызовов там, где важен только результат;
- ассерт на внутреннюю форму промежуточного объекта вместо того, что видит модель на
  другом конце MCP.

Рефактор без смены поведения не должен ронять тест. Перекладка `src/tools/campaigns.ts`
в `tools/campaigns/{schema,handler,tool}.ts` — как раз такой рефактор: тест, который
после неё краснеет, проверял раскладку, а не поведение.

### 4. Тавтологии от моков

Замокан `safeParse` или чистый хелпер, а ассерт проверяет `return` сразу после `if` →
тест проверяет проводку, а не логику. Замени стаб реальной схемой/фикстурой.

**Zod-схемы у нас не мокаются никогда**: схема — это и есть проверяемый контракт, и
именно она конвертирует рубли во входе. Замоканная схема прячет ровно ту ошибку, ради
которой тест писали.

### 5. Аудит моков — реальное поверх стаба

Классифицируй каждый мок:

- **Избавляемый** → заменить реальной реализацией/фикстурой: чистые хелперы `shared/lib`
  (`money`, `id`, `pagination`, `format`), Zod-схемы, разбор ошибок v5. Мок такого
  хелпера — находка, а не граница.
- **Граничный** → оставить, реальный = сеть или реальные траты: глобальный `fetch` к
  `api.direct.yandex.com`, `Date.now()` и таймеры, `process.env` с токеном.
- **Недостижимая ветка** (реальная зависимость не бросает / не доводит до ветки, напр.
  защитный `catch`) → мок оправдан, но требуй комментарий в тесте.

**Сеть — граница, и подменяется целиком, а не по кусочку**: весь транспорт разом через
`installFetchMock()`, а не отдельные его куски. Хороший unit-тест Директа делает две вещи
и обе проверяет:

- **что ушло**: URL, заголовки (`Client-Login` для агентского токена), и главное — тело
  запроса. Деньги в теле обязаны быть **микроединицами**, ID — строками.
- **что вернулось**: ответ песочницы/фикстура прогоняется через реальный разбор, и
  ассерт стоит на том, что инструмент отдал наружу — рубли, строковые ID, разобранные
  per-item ошибки.

Тест, который проверяет только первое, пропускает половину маппинга.

Реальную форму ответа Директа, когда неочевидна, выясняй **эмпирически** (одноразовый
probe против песочницы: вызови, залогируй ответ, сохрани как фикстуру, probe удали) — не
угадывай по документации.

### 6. Честность про уровень

Unit-тест со подменённым `fetch` проверяет маппинг запроса и разбор ответа, а не то, что
Директ такой запрос примет. Это норм как регрессионный сторож — но не описывай его как
проверку интеграции. Реальный контракт API проверяет только `*.int.test.ts` в песочнице.

Сюда же — несоответствие имени файла уровню: настоящая сеть или реальные таймеры в
`*.unit.test.ts`.

### 7. Ложно-зелёные конструкции

Тест, зелёный всегда, что бы ни делал код, — хуже пустышки:

- вызов хендлера без `await` — ассерты бегут до сеттла промиса;
- `expect` внутри `then`/`catch`/колбэка без `await` и без `expect.assertions(n)`;
- `rejects`/`resolves` без `await`;
- ассерт внутри `if`/цикла, который может не выполниться ни разу;
- остатки `it.skip`/`it.only`, закомментированные ассерты;
- подменённый `fetch`, который тест забыл проверить на **факт вызова**: хендлер
  свалился раньше запроса, а ассерты на разбор просто не дошли.

### 8. Слабые ассерты

`toBeDefined`/`toBeTruthy`, когда известно точное значение; `toHaveBeenCalled()` без
проверки аргументов; `not.toThrow` как единственный ассерт; `expect.anything()` в
ключевой позиции; для Zod — `success === false` без проверки, **какая** ошибка и по
какому полю.

Доменные частные случаи, которые особенно любят прятаться за слабым ассертом:

- **Деньги.** `expect(body.Bid).toBeDefined()` вместо `expect(body.Bid).toBe(30_000_000)`
  пропустит и потерянный, и лишний множитель. Проверяй точное число микроединиц в теле
  запроса и точные рубли в выдаче.
- **ID.** `expect(typeof id).toBe("string")` пропустит округление. Бери в фикстуру
  настоящий 19-значный ID и сверяй **посимвольно**: `expect(id).toBe("12345678901234567")`.
  Ассерт на `Number` или сравнение с числовым литералом — сам по себе дефект.
- **Ошибки v5.** Директ отдаёт ошибку запроса телом с HTTP 200; per-item ошибки лежат в
  `*Results`, обрезанная выборка — в `LimitedBy`. Ассерт «просто бросило» не отличает
  эти три случая друг от друга — проверяй код и то, какой элемент не прошёл.

### 9. Подгонка под реализацию

По диффу из фазы 0 п.4: ассерт ослаблен или кейс удалён — особенно в одном диффе со
сменой поведения исходника. Останови и спроси: осознанная смена контракта или заглаженный
баг? Не принимай ослабление молча как «мелочь консистентности».

### 10. Изоляция и порядок

Общая мутируемая фикстура уровня модуля (объект кампании, массив фраз), которую тест
мутирует; невосстановленный мок `fetch`, протекающий в соседний файл; невосстановленные
`vi.spyOn`/fake timers/`vi.stubGlobal`/`vi.stubEnv`. Файл обязан быть зелёным при любом
порядке тестов — подозрение подтверждай пробой (фаза 1.5 п.2).

`vi.resetModules()` — отдельный случай, и это **дефект**, а не стилевая придирка: сброс
графа модулей уносит подмену транспорта (она живёт в переменной модуля `shared/api/fetch.ts`),
и хендлер получает свежую копию с настоящей сетью. Модульное состояние сбрасывается своим
экспортом — образец `clearDictionaryCache` в `tools/dictionaries/handler.ts`.

Для `*.int.test.ts` добавляется своё: песочница — **общее изменяемое состояние**. Тест,
создающий кампанию, обязан за собой убирать или работать с уникальным именем; иначе
второй прогон краснеет на дубле, и это не регрессия кода.

### 11. Описание vs тело

`it("...")` обещает одно, ассерты проверяют другое → отчёт о падении будет врать
разбирающемуся. Заодно сверь конвенции: русский, «должен …»/«при …».

### 12. Зависимость от реальных суток

Тест обязан быть зелёным в любой день, а не только в день написания. Особенно важно для
`get_statistics` и `get_changes`, где период и `Timestamp` — часть контракта.

Ищи данные, посчитанные по живым часам мимо `setSystemTime`: **аргументы `it.each` и
константы уровня модуля вычисляются на сборке кейсов — до `beforeEach`**, поэтому
замороженное время на них не действует. Внутрь кейса такие даты передавай ленивыми
(`() => ...`).

Сюда же — нарушение инварианта «Детерминизм» из `CLAUDE.md`: `Date.now()` внутри хендлера
делает его непроверяемым. Наткнулся на такой хендлер во время ревью — это находка про
исходник, сообщи о ней отдельно (см. фазу 2 п.4).

## Фаза 1.5 — Эмпирические пробы

Чтение даёт подозрения, пробы — доказательства. Прогоны дешёвые (весь unit-набор — меньше
секунды), не пропускай их.

1. **Пробелы покрытия.** `npx vitest run <тесты> --coverage --coverage.include=<исходник>`
   (оба флага обязательны). Непокрытые ветки классифицируй: реальный кейс → предложи
   тест; защита от невозможного → упомяни; инфраструктура → пропусти. Ревью, которое
   только удаляет тесты, смещено — пробел такая же находка, как дубль.
2. **Порядок.** `npx vitest run <файл> --sequence.shuffle.tests --sequence.seed=N` для
   2–3 разных N. Красное на любом сиде = подтверждённый дефект изоляции.
3. **Мутационная проба.** Для каждого теста, подозреваемого по критериям 2, 7, 8:
   временно сломай в исходнике ветку, которую он якобы проверяет, прогони тест. Не
   покраснел — дефект доказан, укажи мутацию в отчёте.

   Доменные мутации, которые обязаны ронять набор:
   - убрать множитель `1_000_000` в конвертации денег;
   - вернуть ID через `Number(...)` вместо строки;
   - разобрать ответ через нативный `JSON.parse` вместо `json-bigint`;
   - при update отправить только новый элемент вместо объединённого списка
     (инвариант «Update = полная замена»).

   **Всегда откатывай мутацию** (`git checkout -- <исходник>` если он был чистым, иначе
   восстанови сохранённую копию) и перепрогони зелёное перед следующим шагом.

## Фаза 2 — Правки и проверка

1. Внеси согласованные правки (по умолчанию — безопасные удаления дублей/механики и
   замены избавляемых моков; спорное — предложи, не навязывай).
2. Прогон: `npx vitest run <файлы>` → зелёное.
3. `npx biome check <файлы>` и `npm run typecheck`.
4. Правь **тест, а не исходник**. Исключение — ревью вскрыло реальный баг (потерянный
   множитель, ID через `Number`, `Date.now()` в хендлере): тогда останови и сообщи, не
   заглаживай подогнанным тестом.

## Фаза 3 — Отчёт

- Находки, отсортированные по важности: `файл:строка` → дефект → что сделано/предложено.
  Для доказанных пробами — какая проба (мутация/shuffle/coverage) подтвердила.
- Пробелы покрытия с предложенными кейсами (или «пробелов нет»).
- Что осознанно **не** трогал и почему (граничные моки, недостижимые ветки).
- Итог прогона (vitest / biome / typecheck) и подтверждение, что все мутационные пробы
  откачены.
- Открытые вопросы и предложение по коммиту. Коммит — по правилам скилла `git-commit`:
  правки тестов идут **отдельным `test`-коммитом**, а если правится свой же тест из этой
  незамерженной ветки — `--fixup` на тестовый коммит, а не новый `test(...)`.
  Подтверждение пользователя перед коммитом обязательно.
